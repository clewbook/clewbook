# Known limitations

Moved here from the README on 14 October 2026; updated on 22 October 2026. The threat model is in [THREAT_MODEL.md](THREAT_MODEL.md).

- **A payment message whose refund cannot be paid is rejected at once.** A hand built payment code whose refund address is not a valid Orchard or Ironwood address, or that leaves nothing after the fee, gets a signed reject with a reason code, holds no lock and cannot stop the close; the recount upholds that reject even if its sender publishes their secret (SPEC §2, "The validity rule"). Before 2026-10-13 such a payment could make an honest host's recount fail and stop the close; a host that already holds one should run the current version, whose next watch pass writes the reject.
- **The host can spend a contribution that has a ticket.** The host holds the campaign key. The host program keeps such notes out of ordinary use, but that is a mark in the host's own wallet, not a rule of the network. If the host spends one anyway, the ticket stops working and the recount shows the spend afterwards (R5 before the deadline, R6 after it). It is shown, not prevented. Signing by several parties, so that no single party can move the money, is on the roadmap ("Shared custody"); it is research, not built.
- **An early close height is the host's own statement too.** In a fundraiser whose rules switch on early close at creation (an auction never can), the host may close before the deadline once the goal is met; a host could write an earlier close height to leave out a payment whose ticket it held back; that payment would then count as late and stay in the campaign wallet. If the payment's ticket was already on the list, the recount fails (R3). Otherwise the recount only lists such payments under R2, because an honest early close can have them too (threat 26 in docs/THREAT_MODEL.md).
- **A hard cap refunds what does not fit, at the close.** In a fundraiser with a hard cap (`cap_zat` in the rules), payments are taken in chain order at the close: each one that fits under the cap is kept, a later, smaller one can still fit, and the goal (the soft cap) is counted on what is kept. A payment that does not fit is refunded whole by its own ticket when the campaign closes, minus the refund fee, and its money stays locked until then. The contribute page shows the room left and refuses a larger amount, but it reads the room from the public list, so it cannot see payments taken back, and a relay that hides entries would make the room look larger. Someone can also fill the cap and take their payments back just before the close, so that others wait; it costs them only fees. A host that keeps a payment over the cap is caught by R6.
- **When a ticket was issued is the host's own statement.** The ledger entry carries the block height at which the host says it issued the ticket, and the recount compares that height with the payment's height. A host that issued a ticket late could write an earlier height and the recount would not notice. Today the relays are run by the same people as the host, so their records do not help. A relay run by someone else could record when it first saw each ticket; that is planned, not built.
- **The host sees every bid** (except in a blind bid auction). In an auction the host's wallet opens every payment, so the host sees each bid amount as it arrives. Nothing stops the host from bidding itself from another wallet after seeing the others, and nothing detects it. Bid amounts stay off the public record until the close; they are not hidden from the host. A blind bid auction ([BLIND_BIDS.md](BLIND_BIDS.md); on the main network only if it ends before the NU7 upgrade) hides each bid from the host too until after the close; its own limits are in section 3 of that file.
- **The recount page is served by the project's own server.** A visitor who does not want to trust that server can build the command line recount (`cb-recount`) from this repository and run it.

- **Payments that arrive after the deadline are not counted and not refunded.** A payment mined after the deadline gets no ticket and no ledger entry, the close neither refunds nor sweeps it, and it stays in the campaign wallet. The host can list such payments with `cb-host late --run <campaign folder>` (tested on the testnet on 2026-10-10: it listed exactly the two bids of one test campaign that were mined after its deadline). Returning them is a manual step for the host today, with the ordinary wallet tools; a "return late payments" command is a future feature. Two exceptions send such payments back on their own, minus the network fee: a payment that arrives after a cancel ("cancel and refund all", below), and a deposit after the deadline in a blind bid auction. What the payer sees has not been tested with a real late payment; from the page's code, a fundraiser payer whose page saw the payment is told after the ticket window that their refund ticket has not arrived and to keep the backup file and ask whoever runs the campaign, and in an auction the bid page, which cannot see bids before the close, keeps waiting for the payment.
- **A host that loses its connection to the chain server.** The host's connection now has a time limit: connecting must finish within 20 seconds, and a connection that goes silent later is detected by keepalive pings (every 30 seconds, 20 seconds to answer). A check that hits a stalled server therefore ends with an error and the next check, 15 seconds later on the dashboard, tries again (tested with a stand-in server that accepts the connection and never answers: the check gave up after 20 seconds; the same code without the limit was still waiting after 90 seconds). The dashboard then says that the last check failed and that new payments get no tickets until it can reach the server. Before this change a stalled check could hang for good, and the dashboard warned only once 3 minutes had passed without a finished check; that warning still exists for a program that stops checking altogether. Not covered: a server that completes the connection and keeps answering the keepalive pings but never answers a request (that would need a time limit per request). The dashboard's wording in this case was not re-tested with a stalled server.
- **A cancel costs each contributor the network fee.** In a fundraiser that opted in to "cancel and refund all" (also a presale with a hard cap), the host can cancel at any time before the deadline, even after the goal is met. Every contribution comes back by its own ticket, minus the refund fee fixed in the campaign's rules (`refund_fee_zat`); the host does not top it up (on the roadmap). Campaigns made without the opt in cannot be cancelled. On the main network the host program with cancel runs only after the current mainnet campaigns close; until then it is on the test network only (tested there on 2026-10-21, EVIDENCE.md section 13).
- **The home page can show a campaign's old state for up to an hour.** When a listed campaign's relay or the chain cannot be reached, the listing keeps showing the campaign's last good state for up to 1 hour, then takes it off. A relay that answers wrongly takes it off at once.
- **A host's suggested name is checked against a word list, not judged.** A host may suggest the name shown as "Hosted by". The listing refuses reserved words in any spelling, and the operator approves the host before the name appears, but nobody checks who the host really is.
